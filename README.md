# DeepSeek Agent — День 6–10

Локальный веб-чат с отдельной сущностью агента, несколькими диалогами, пресетами и автоматическим сохранением контекста в JSON.

## Возможности

- `Agent` в отдельном файле управляет историей запроса и обращением к LLM через провайдер.
- Несколько диалогов: создание, переименование, удаление, экспорт и импорт.
- Каждый диалог автоматически записывается после сообщения и восстанавливается после перезапуска.
- Пресеты содержат системный промпт и параметры DeepSeek.
- В одном диалоге можно переключать пресеты или применять разовые настройки.
- Для каждого запроса сохраняется точный снимок настроек, даже если исходный пресет позднее изменён.
- Reasoning не смешивается с ответом: `reasoning_content` хранится отдельно и показывается только в раскрываемом блоке.
- Технические данные включают время ответа, модель, request ID, fingerprint, причину завершения, входные, выходные, кэшированные, некэшированные и reasoning-токены.
- Возле каждого запроса явно показан точный размер отправленного контекста и его разбиение на кэшированные и некэшированные токены.
- Возле ответа показаны выходные, reasoning-токены, итог текущего вызова и накопленный итог на этом шаге диалога.
- В шапке отображаются суммы входных, выходных, кэшированных и всех токенов за диалог.
- JSON записывается атомарно, чтобы прерванная запись не повредила основной файл.
- Режим контекста задаётся отдельно для каждого диалога: полная история, summary, Sliding Window, Sticky Facts или Branching.
- При сжатии последние 5 обменов остаются дословно, а каждые 5 более старых обменов сворачиваются.
- Все исходные сообщения, действующий summary, предыдущие версии и токены суммаризации сохраняются в JSON.
- Sliding Window отправляет только последние N обменов; N настраивается от 1 до 50.
- Sticky Facts автоматически обновляет key-value память после каждого сообщения пользователя только в этом режиме.
- Facts можно добавлять, редактировать, закреплять, откреплять и удалять вручную.
- Branching создаёт дерево от любого сообщения, сохраняет исходные пути и переключает соседние ветки через 1/N.
- Голосовой ввод работает полностью локально через `whisper.cpp`, Vulkan и RX 6600.
- Модель `large-v3-turbo` загружается при старте и остаётся в видеопамяти до закрытия приложения.

## Установка в Windows

Нужен Python 3.10 или новее. В PowerShell из папки проекта выполните:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
Copy-Item .env.example .env
notepad .env
```

Укажите ключ и одну из поддерживаемых текстовых моделей:

```dotenv
DEEPSEEK_API_KEY=ваш_настоящий_ключ
DEEPSEEK_MODEL=deepseek-v4-flash
```

Ключ не записывается в историю или экспорт.

## Локальный голосовой ввод

Голосовое распознавание не использует облачный API и ничего не отправляет в интернет. Компоненты хранятся внутри проекта:

```text
models/ggml-large-v3-turbo.bin       модель Whisper
tools/whisper/bin/whisper-server.exe постоянный Vulkan-сервер
tools/ffmpeg/bin/ffmpeg.exe          переносимый конвертер аудио
```

Для первой установки дважды щёлкните `setup_voice.bat`. Скрипт:

1. проверит Vulkan SDK и Visual Studio Build Tools;
2. скачает официальный исходный код `whisper.cpp`;
3. скачает модель `large-v3-turbo` и проверит её SHA-1;
4. положит portable FFmpeg внутрь проекта;
5. соберёт `whisper-server.exe` с `GGML_VULKAN=ON`.

При обычном запуске `run.bat` Whisper стартует в фоне одновременно с чатом. Модель загружается один раз и остаётся в памяти RX 6600. Кнопка микрофона станет доступна после статуса **«Whisper готов»**. Повторное нажатие останавливает запись, распознанный текст подставляется в поле ввода и не отправляется автоматически.

Для остановки нажмите `Ctrl+C` в консоли приложения: дочерний Whisper-процесс завершится и освободит видеопамять. Аудиозаписи не сохраняются на диск и не добавляются в JSON диалогов.

## Запуск

Дважды щёлкните `run.bat` или выполните:

```powershell
.\run.bat
```

Браузер откроет локальный адрес автоматически. Если порт `5000` занят, программа выберет следующий свободный порт. Остановка — `Ctrl+C` в консоли.

## Где хранится история

```text
data/
├── presets.json
└── conversations/
    └── <id-диалога>.json
```

Папка `data` добавлена в `.gitignore`, потому что это пользовательские данные. Для переноса используйте кнопку **«Экспорт JSON»**. Экспорт содержит диалог и снимки задействованных пресетов; импорт создаёт отдельную копию и не перезаписывает существующий диалог.

## Настройки запроса

- `model` — `deepseek-v4-flash` или `deepseek-v4-pro`;
- системный промпт;
- `temperature` и `top_p`;
- reasoning и `reasoning_effort` (`low`, `high`, `max`);
- необязательный `max_tokens`;
- до 16 стоп-последовательностей;
- обычный текст или JSON-объект;
- `logprobs` и необязательный `top_logprobs`.

В reasoning-режиме DeepSeek принимает `temperature` и `top_p`, но они не влияют на генерацию. Приложение всё равно сохраняет переданные значения. `seed`, `frequency_penalty` и `presence_penalty` не предлагаются: DeepSeek их не поддерживает либо больше не применяет.

## Структура проекта

Разделение `Agent` и `ChatProvider` оставляет точку расширения для OpenAI или другого провайдера, но текущая версия выполняет только реальные запросы DeepSeek.

## Как считаются токены

Счётчики берутся из фактического поля `usage` ответа DeepSeek, а не оцениваются по длине текста. **Контекст вызова** — это весь вход, который модель получила в конкретном запросе: системный промпт, выбранная версия истории и новое сообщение. **Σ диалога** — сумма `total_tokens` всех завершённых ответов; повторно отправленная история учитывается на каждом шаге. `Reasoning` показан как отдельная детализация выходных токенов и не прибавляется к общему итогу второй раз.

## Сжатие истории — День 9

В правой панели **«Контекст»** выбирается режим конкретного диалога:

- **Полная история** — в каждый запрос передаются все успешные обмены;
- **Summary + последние обмены** — передаётся накопительный summary и несжатый хвост истории.

Один обмен — это успешная пара `user + assistant`. Последние 5 обменов всегда передаются дословно. Когда перед ними накапливаются ещё 5 несжатых обменов, приложение вызывает `deepseek-v4-flash` с `reasoning=false`, создаёт новую версию summary и сворачивает в неё эту пятёрку. Поэтому несжатый хвост содержит от 5 до 9 обменов. На первом включении режима накопившаяся история обрабатывается последовательными группами по 5.

Summary добавляется к системному контексту основного запроса. Переключение обратно на полную историю не удаляет ни сообщения, ни созданные версии. В каждом ответе поле `technical.context_management` показывает, какой режим и какая версия summary реально использовались.

Файл `data/conversations/<id>.json` содержит:

- `messages` — полную исходную историю;
- `context_management` — режим диалога и ID действующего summary;
- `summaries` — неизменяемые версии, ID охваченных обменов и сообщений, модель и фактический `usage`;
- `summary_token_totals` возвращается API и показывает отдельную стоимость создания памяти.

Расход на обычные ответы и на суммаризацию показан раздельно. Для ручного сравнения задайте одинаковые вопросы в двух диалогах: в одном оставьте полную историю, во втором включите сжатие.

Стоимость намеренно не рассчитывается: приложение сравнивает только использование токенов и не привязано к тарифам.

Если реальный запрос превышает лимит контекста выбранной модели, API-вызов завершается ошибкой. Программа сохраняет неотправленное сообщение как неудачное, не добавляет его в будущий контекст и явно предлагает создать новый диалог или сократить историю.

## Стратегии контекста — День 10

В панели **«Контекст»** доступны пять режимов:

- **Полная история** — весь успешный активный путь;
- **Summary** — существующая накопительная суммаризация;
- **Sliding Window** — текущий запрос и последние N обменов, включая текущий незавершённый обмен;
- **Sticky Facts** — структурированные facts плюс такое же окно из N обменов;
- **Branching** — полный активный путь выбранной ветки.

Для Sliding Window и Sticky Facts значение N настраивается от 1 до 50, по умолчанию 5.

Sticky Facts используют универсальные группы ключей: `goal`, `context`, `entities`, `requirements`, `constraints`, `preferences`, `decisions`, `agreements`, `resources`, `environment`, `numbers`, `deadlines`, `definitions`, `output`, `open_questions`, `next_steps`, `risks`. Автоматическое обновление выполняет `deepseek-v4-flash` без reasoning и сохраняет отдельный фактический usage. Если извлечение не удалось, основной ответ продолжает использовать предыдущую память, а ошибка остаётся в `fact_revisions`.

В режиме Branching кнопка **«Разветвить»** доступна после каждого сообщения. После сообщения пользователя сразу создаётся новый вариант ответа DeepSeek. После ответа ассистента открывается пустое продолжение для нового пользовательского промпта. Исходная ветка имеет номер 1; следующие ветки в этой точке получают номера 2, 3 и далее. Удаление веток не предусмотрено.

Все сообщения дерева хранятся один раз в `messages` и связаны через `parent_id`. Текущий лист записан в `context_management.active_leaf_id`; facts, их ревизии, summaries и ветки остаются в одном JSON-файле диалога. Старые линейные JSON-диалоги мигрируют при чтении без удаления исходных сообщений.

## Проверка

```powershell
.\.venv\Scripts\python.exe -m unittest -v
```

Тесты проверяют все стратегии, окна 1–50, автоматические и ручные facts, закрепление, обе разновидности ветвления, переключение веток, старый summary, перезапуск JSON-хранилища, настройки, токены, ошибки и импорт/экспорт. Они используют подменённый провайдер и не расходуют средства API. Реальный вызов требует действующего ключа и сети.
